# hookify-cli

[![npm version](https://img.shields.io/npm/v/hookify-cli.svg)](https://www.npmjs.com/package/hookify-cli)
[![license](https://img.shields.io/npm/l/hookify-cli.svg)](LICENSE)

Zero-config CLI client for [Hookify](https://github.com/BarneyMayerson/hookify). Fetch and update local `.git/hooks` with a single command — and, when you're ready, migrate an existing ESLint + Prettier setup to OXC.

## Install

No install needed — just run it with `npx`:

```bash
npx hookify-cli sync
```

(`npm install -g hookify-cli` works too, if you'd rather have `hookify` on your `PATH` directly.)

## `sync` — keep your local hooks up to date

```bash
HOOKIFY_TOKEN=hk_live_... HOOKIFY_API=https://your-hookify-instance/api/v1 npx hookify-cli sync
```

Get your `HOOKIFY_TOKEN` and the exact command (pre-filled with your project's token and API URL) from your project's page in the Hookify dashboard.

That's it — `sync` fetches your project's current check configuration and writes the matching `pre-commit` and/or `commit-msg` hooks into `.git/hooks`.

What it does, specifically:

- Writes only the hook types your project actually has checks enabled for — no empty hook files, and a hook is removed again if you later disable every check of that type.
- **Never overwrites a hook it doesn't own.** If `.git/hooks/pre-commit` already exists and wasn't generated by Hookify (e.g. Husky), it's backed up to `pre-commit.backup.<timestamp>` before being replaced, and you're told about it. A hook Hookify *did* generate is safely overwritten on every `sync`.
- Works offline: if the API is unreachable or returns a server error, `sync` falls back to the last cached manifest instead of blocking your workflow, and tells you why. On a brand-new checkout with no cache and no network, it skips installing anything rather than guessing.
- **Notices a dead token.** If the API answers `401` (the token was revoked, or the project was deleted in the dashboard), `sync` does *not* fall back to the cache — that would mean silently running stale checks for a project that no longer exists. Instead it removes the hooks it installed (only the ones carrying its marker; hooks it doesn't own are never touched), clears its cache, tells you what happened, and exits with a non-zero status.
- Refuses to run in a monorepo (multiple `package.json`/`composer.json` in one repository) rather than silently doing the wrong thing — this is a known limitation, not an oversight.

## `migrate` — move an existing project to OXC

```bash
npx hookify-cli migrate
```

If your repo has a flat `eslint.config.js`, this runs [`@oxlint/migrate`](https://www.npmjs.com/package/@oxlint/migrate) and `oxfmt --migrate prettier` against it, shows you a `git diff --stat` summary of what changed (including any rules that couldn't be auto-migrated), and — only if you confirm — commits the result to a new local branch (`hookify/migrate-to-oxc`).

It deliberately stops there: `migrate` never pushes or opens a pull request on its own. Review the branch, then push and open the PR yourself:

```bash
git push -u origin hookify/migrate-to-oxc
```

(Automating the push-and-PR step is on the roadmap — it needs a GitHub-scoped token the CLI doesn't hold today, so it's a separate piece of work rather than something bolted on half-safely.)

Requirements for `migrate`: a clean working tree, and a `eslint.config.js` in the repo root (legacy `.eslintrc*` isn't supported yet).

## Security notes

- Everything written into a generated hook file comes from either Hookify's fixed check catalog (trusted, not user-editable) or your project's name (free text). The project name is sanitized before being embedded, so it can't break out of its context in the generated script.
- `sync` never phones home with anything beyond the manifest request itself — no telemetry, no analytics.
- Installed hooks are plain shell scripts that run your local tools; they never contact Hookify. Only `sync` talks to the API — which is also why a deleted project's hooks are cleaned up the next time someone runs `sync`, not instantly.
