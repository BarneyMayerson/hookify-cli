# hookify-cli

[![npm version](https://img.shields.io/npm/v/hookify-cli.svg)](https://www.npmjs.com/package/hookify-cli)
[![license](https://img.shields.io/npm/l/hookify-cli.svg)](LICENSE)

Zero-config CLI client for [Hookify](https://github.com/BarneyMayerson/hookify). Fetch and update local `.git/hooks` with a single command — and, when you're ready, migrate an existing ESLint + Prettier setup to OXC.

## Install

No install needed — just run it with `npx`:

```bash
npx hookify-cli sync
```

(`npm install -g hookify-cli` works too, if you'd rather have `hookify` on your `PATH` directly.)

## `sync` — keep your local hooks up to date

```bash
HOOKIFY_TOKEN=hk_live_... HOOKIFY_API=https://your-hookify-instance/api/v1 npx hookify-cli sync
```

Get your `HOOKIFY_TOKEN` and the exact command (pre-filled with your project's token and API URL) from your project's page in the Hookify dashboard.

That's it — `sync` fetches your project's current check configuration and writes the matching `pre-commit` and/or `commit-msg` hooks into `.git/hooks`.

What it does, specifically:

- Writes only the hook types your project actually has checks enabled for — no empty hook files, and a hook is removed again if you later disable every check of that type.
- **Never overwrites a hook it doesn't own.** If `.git/hooks/pre-commit` already exists and wasn't generated by Hookify (e.g. Husky), it's backed up to `pre-commit.backup.<timestamp>` before being replaced, and you're told about it. A hook Hookify *did* generate is safely overwritten on every `sync`.
- Works offline: if the API is unreachable or returns a server error, `sync` falls back to the last cached manifest instead of blocking your workflow, and tells you why. On a brand-new checkout with no cache and no network, it skips installing anything rather than guessing.
- **Notices a dead token.** If the API answers `401` (the token was revoked, or the project was deleted in the dashboard), `sync` does *not* fall back to the cache — that would mean silently running stale checks for a project that no longer exists. Instead it removes the hooks it installed (only the ones carrying its marker; hooks it doesn't own are never touched), clears its cache, tells you what happened, and exits with a non-zero status.
- Refuses to run in a monorepo (multiple `package.json`/`composer.json` in one repository) rather than silently doing the wrong thing — this is a known limitation, not an oversight.

## `migrate` — move an existing project to OXC

```bash
npx hookify-cli migrate
```

For a repo with a flat `eslint.config.js`, this does the whole move to [oxlint](https://oxc.rs) and oxfmt on a new local branch (`hookify/migrate-to-oxc`), step by step:

1. Runs [`@oxlint/migrate`](https://www.npmjs.com/package/@oxlint/migrate) on your ESLint config and writes `.oxlintrc.json`. Rules with no oxlint equivalent (many `vue/*` rules, for example) are reported as skipped — review that list.
2. Runs `oxfmt --migrate prettier` and writes `.oxfmtrc.json` (options, overrides, `.prettierignore` patterns, Tailwind plugin settings).
3. If your Prettier config used `prettier-plugin-organize-imports` — which oxfmt can't load — turns on oxfmt's built-in `sortImports` so imports stay sorted. Its algorithm is similar to `eslint-plugin-perfectionist`, not TypeScript's `organizeImports`, so some imports may be reordered. An explicit `sortImports` already in the config is left alone.
4. Installs `oxlint` and `oxfmt` as devDependencies, using your package manager (read from the `packageManager` field or your lockfile: npm, pnpm, yarn or bun). Packages you already depend on are skipped. This runs your package manager for real, including any lifecycle scripts your project defines.
5. Formats the two generated config files.
6. Shows exactly what will be committed (the staged changes), and — only if you confirm — commits it.

**What it never does:** push, open a pull request, remove ESLint or Prettier, edit your `package.json` scripts, or reformat your codebase. Do the last one yourself, as a separate commit:

```bash
npx oxfmt
```

### Safe to abandon

If you decline, a step fails, or the tools turn out to change nothing, `migrate` rolls back to where you started: you're back on your original branch, the migration branch is deleted, `package.json` and the lockfile are restored, and the generated files are removed. It only touches the files it can create itself (`.oxlintrc.json`, `.oxfmtrc.json`, `package.json` and the lockfiles) — anything else in your working tree is left alone, and it tells you if there is any. Packages it installed stay in `node_modules`; git doesn't track those.

If the commit itself is rejected (for example by a pre-commit hook), the work is *not* thrown away: it stays staged on the migration branch, and you're told how to proceed.

### After the migration

```bash
git push -u origin hookify/migrate-to-oxc
```

Then, before merging:

1. Run `npx oxfmt` and commit the result separately. oxfmt follows Prettier closely but not perfectly, so some files will change.
2. In the Hookify dashboard, switch the project's checks from ESLint/Prettier to oxlint/oxfmt, then run `hookify sync`. Do this *after* step 1 — the oxfmt check covers the whole repository and would otherwise fail on every commit.
3. Remove ESLint and Prettier once you're happy with the result.

(Opening the pull request automatically is on the roadmap — it needs a GitHub-scoped token the CLI doesn't hold today, so it's a separate piece of work rather than something bolted on half-safely.)

**Requirements:** a clean working tree (untracked files included), and both `eslint.config.js` and `package.json` in the repository root. The legacy `.eslintrc*` format isn't supported yet.

## Security notes

- Everything written into a generated hook file comes from either Hookify's fixed check catalog (trusted, not user-editable) or your project's name (free text). The project name is sanitized before being embedded, so it can't break out of its context in the generated script.
- `sync` never phones home with anything beyond the manifest request itself — no telemetry, no analytics.
- Installed hooks are plain shell scripts that run your local tools; they never contact Hookify. Only `sync` talks to the API — which is also why a deleted project's hooks are cleaned up the next time someone runs `sync`, not instantly.
